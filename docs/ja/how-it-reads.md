# リプレイの読み取り方 {#how-it-reads-a-replay}

リプレイは、JSON のブロックのヘッダーと、ゲームのパケットの流れでできています（フォーマットのメモは [`heat3d_ext_wows/bigworld.py`](https://github.com/Holdi601/3DHeat-Ext-WoWs/blob/main/heat3d_ext_wows/bigworld.py) にあります）:

- 最初のブロックは、暗号化されていない状態で入っています: マップ、クライアントのバージョン、録画しているプレイヤーと艦船、そして名簿（各プレイヤーの名前、味方か敵か、艦船の番号）。新しいクライアント（15.x）では、さらに 2 つのブロックが加わります。1 つは空、もう 1 つは録画しているプレイヤーのアカウントと戦闘の ID をテキストで持ち、`blockIds` に読まれます。結果は JSON には入っていません。15.x はそれをパケットの流れの中に保存します。
- パケットの流れ。zlib で圧縮され、ゲームが持つ鍵で Blowfish で暗号化されています。この鍵は、これらのファイルを読むコミュニティのツールが公開しています。復号すると、次のものが入っています:
  - クライアントが見ることのできたすべての艦船について、エンジンの位置の更新（自分のチームは最初から最後まで、敵は発見されている間、または近くにいる間）。動いている間は 1 秒に何回か、動いていないときはそれより少なく；
  - 録画しているプレイヤー自身の艦船。独自のパケットに入っており、1 秒に約 7 回；
  - 最初に一度だけ、プレイヤーの記録がピクルされた Python のリストとして。これらは、ストリーム内のどのエンティティがどのプレイヤーかを示します。そのキーには番号が振られており、番号はパッチによって変わるので、読み手はキーをその値で見つけます: 名簿の名前を持つキーと、位置の更新を持つエンティティを持つキー；
  - 艦船が沈んだことをクライアントに知らせるサーバーの呼び出し: 犠牲者、キラー、原因。これは番号ではなく、その形（12 バイト。最初の 2 つは艦船のエンティティ。犠牲者は 1 回ずつ現れる）で見つけます；
  - 各艦船のダメージ: 命中ごとの（攻撃者、ダメージ）の配列。命中した艦船の上にあります。そして体力。少し前に設定されたプロパティです；
  - クライアントが知らされた、すべての砲弾と魚雷の一斉射撃: 砲弾の種類、射手、一斉射撃、そして各砲弾または魚雷の開始位置と速度；
  - 砲弾の終点: 射手、命中の種類、それぞれの場所（15.x のクライアントでは、命中したところの砲弾についてさらに情報があり、それは読み飛ばされる）；
  - チャット: 送信者、チャンネル、行；
  - 録画しているプレイヤーへのピクルされた呼び出し: そのダメージの統計、プレイヤーの記録の更新、戦闘の状態；
  - 15.x のクライアントでは、戦闘の終わりの結果: 独自のパケットで、戦闘の ID を持つ JSON オブジェクト。マッチドキュメントの `results` に丸ごと読まれます（ゲーム自身のリスト。名前は付いていない: `commonList`、`privateDataList`、アカウントごとの `playersPublicInfo`、...）。

確認したバージョン間で違うパケットとメソッドの番号（自分の艦船のパケットは 43 または 44、沈没の呼び出しは 76 または 83、砲弾は 101、102、126 または 127）は、すべて形で見つけます（[`heat3d_ext_wows/stream.py`](https://github.com/Holdi601/3DHeat-Ext-WoWs/blob/main/heat3d_ext_wows/stream.py) を参照）。そのため、番号を振り直すパッチがあってもテーブルは空になりません。見つかった番号は、マッチドキュメントの `decoded` にあります。

**ピクルは信用できないデータです。** リプレイはどこからでも来るファイルで、ピクルは実行するコードを名指しできます。そのため、ピクルに名指しされたすべてのクラスや関数を、中身のないプレースホルダーに置き換えるアンピクラーで読み込みます。これで作られるのは普通のデータだけで、ほかは何も作られません。テストでは、`os.system` を呼び出すピクルを与えて確かめています。

**撃沈**は、呼び出しの正確な時刻を持ちます。その場所は、犠牲者が最後に見られた場所です。それが 5 秒以内だった場合に限ります。**戦闘の開始**は、どの艦船かが初めて動いた瞬間です（艦船はカウントダウンの間は静止しています）。

テーブルの行ではないものはすべて、[マッチドキュメント](match-document.md) にあります。

**クライアントに知らされたこと**は、自分のチームについては完全で、敵については部分的です。敵の射撃、命中、体力は、範囲内にいる間は含まれています。

**読まないもの:**

- 航空機とその飛行隊（それらを運ぶ呼び出しは分解されていません）、ミニマップの視界の更新（詰められている）、発見、リボン、火災と浸水（それ自体のイベントとしては。そのダメージは命中の中にあります）、消耗品、占領ポイントとチームのスコア（定義のないエンティティのプロパティ。形では区別できませんでした）、艦船のプロパティの残り（照準、舵、速度の設定など）。
- プレイヤーの記録とダメージの統計のキーの番号を名前として: ゲームが番号を振っており、その番号は変わります。番号のまま残されます。
- 砲弾が当たったところでの追加のデータ（15.x）と、砲弾または魚雷の開始と速度の後のバイト。
- 15.x より前のクライアントの結果: それらのリプレイには入っていません。
- 艦船の番号を名前として: 名前はゲーム自身のパラメーターファイルにあり、リプレイにはありません。

## 読み取りをどう確かめたか {#how-the-reading-was-checked}

読み取りは、0.9 から 15.x までのクライアントの公開されたリプレイで確かめました。各値は、リプレイがもう一度別に与えているものと比べています:

- **位置:** すべての艦船のエンティティは、名簿の名前と一致しました。方位は進行方向と 0.1 ラジアン以内で一致します。沈んだ後、艦船は 0.1 単位未満しか動きません。静止している艦船は、更新が少なくなります。
- **体力:** クライアントの視界の中で沈んだ艦船は、すべて体力 0 で終わります。すべての命中のうち約半分は、その直前 1 秒の体力の低下と一致します。残りは修理や別の命中と一緒に低下します。
- **ゲーム自身の統計との照合:** 最新のクライアントでは、録画しているプレイヤーのダメージの読みは統計の 0.1 % 以内です。古いクライアントでは統計のほうが高くなります。クライアントにすべての命中が送られていないか、統計が命中より多くを数えているためです（未解決）。
- **砲弾:** 砲弾は、その艦船の最後にわかった位置から数単位離れたところで始まります（砲は船体に沿って並んでいます）。ほぼすべての砲弾の終点は、1 分以内に、クライアントが見た射撃に続いています。

テストは、同じ形式でリプレイを作るので、このリポジトリには実際のリプレイは残されていません。

**確認していないもの:** 0.9.6 より前のクライアント、Lesta のクライアント（Mir Korabley）、1 つを超える作戦やシナリオ、クランとランク戦、そしてどの艦船の番号がどの艦船かということ。
